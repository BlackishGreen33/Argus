# GitHub Projects 看板流程

本文定义看板如何承载工作状态。它不代表数据库状态、部署状态或发布结论；这些状态分别以 AuditEvent、部署回读和发布检查表为准。

如果启用 GitHub Projects，建议使用名为 `Argus delivery` 的 Board 和以下五列：

| 列          | 用途                           | 进入条件                       | 离开条件                           |
| ----------- | ------------------------------ | ------------------------------ | ---------------------------------- |
| Backlog     | 记录尚未拆出验收的需求或技术债 | 需求、风险或决策已留下来源     | 已写触发动作、预期结果、依赖和验收 |
| Ready       | 等待实现的可执行任务           | 验收条件、依赖和影响文档已明确 | 开始修改代码或文档                 |
| In Progress | 当前正在修改的任务             | 已有分支或工作树               | 自测完成，变更和文档影响已检查     |
| Review      | 等待代码、文档、截图或测试复核 | 相关命令和证据可重跑           | reviewer 已处理意见，发布决定明确  |
| Done        | 已满足验收且记录完整的任务     | 有 commit、验证证据和文档回读  | 后续发现新差异时重新打开           |

每张卡片至少记录 `area`、`milestone`、`risk`、触发动作、预期结果、依赖、验证命令和证据位置。涉及代码或目录变更的卡片必须链接受影响的 README、DESIGN、plan、decision、test、risk 或 release 文档。

## 看板和仓库事实的边界

- Board 只表示任务处理状态，不证明 CI、数据库、Vercel 或 Supabase 当前可用。
- “Done” 仍需满足 [发布前检查表](./release-checklist.md) 的适用门槛。
- 看板字段或列变更时，先更新本文件，再检查 [docs/plan.md](./plan.md) 的里程碑链接。
- 没有实际 Board URL、负责人或同步任务时，不把“建议建立”写成已建立。
